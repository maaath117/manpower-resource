## 阶段目标

还原实际流程，用多角色和多来源材料核实问题。与上一阶段的区别：业务挖掘看"值不值得做"，本阶段看"现场到底怎么做的"，因此必须产出矛盾陈述、异常路径和材料缺口，而不是一条顺滑的理想流程。

## 任务 1 / 3 · 开展角色访谈

**交付物：访谈记录与角色地图**

一、访谈口径与记录方式

六位角色各完成第1轮访谈，围绕"最近一单"展开，先听当事人自述，再用其他角色的陈述交叉核实。事实编号按角色分段：顾明岚 f00–f05、林亦舟 f10–f15、唐映秋 f20–f25、秦芮 f30–f35、傅景 f40–f45、叶书 f50–f55。
上游承接：业务挖掘已确认目标为减少重复核对并保留人工确认与可追溯来源（f00），验收口径为抽查50单至少45单一次给出完整缺件清单（f02），首期只覆盖一个批次、只做材料完整性提示（f05），决策边界为范围由业务负责人定、审核与质量负责人可否决（f04）。

二、按最近一单讲完的完整过程

1. 触发与输入：客户提交入职服务单，材料包进入区域核对（f01 · 顾明岚·第1轮；f20 · 唐映秋·第1轮）。
2. 谁接手——区域核对：一线服务专员林亦舟核对材料完整性。此环节的真实做法是先在企业群消息里沟通确认，再回填表格，因此**回填时间晚于实际发生时间**（f13 · 林亦舟·第1轮）。
3. 补件：流程协调员唐映秋跟踪补件，每次交接记录接收人、版本与未结项（f20）；若交接只写"已处理"，未结项就会挂账、责任无法归属（f23）。
4. 版本判定：按"版本有效期 + 确认状态"两个条件判定，作废记录保留原因，不靠文件名猜最新版（f24）；两边都认为自己是有效版本时转人工复核，未确认项归到对方名下属责任冲突、规则不允许（f25）。
5. 服务确认：一线可提交变更，**正式确认必须由业务负责人完成，模型本身没有审批权限**（f22 · 唐映秋·第1轮）；所有正式结论须授权人员确认，不接受"系统自动定论"或一线代签（f41 · 傅景·第1轮）。
6. 输出与归档：原始版本、修订原因、确认人须可追溯，练习结束按约定删除虚构个人字段（f43）；审计要能还原谁查过、用的哪个版本、提了什么建议、谁确认（f45）。
7. 使用的系统：内部服务台、业务台账、文件库三类，**服务单还没有统一的关联编号**（f30 · 秦芮·第1轮）。

三、角色地图（接手环节 / 系统 / 交接对象 / 返工点）

- 顾明岚·业务负责人：定范围与业务目标（f04、f05）；系统=业务台账查看；交接对象=流程协调员与审核负责人；返工点=范围反复收窄
- 林亦舟·一线服务专员：区域核对与异常第一发现（f10、f11）；系统=服务台 + 群消息 + 表格回填（f13）；交接对象=流程协调员；返工点=清单版本不一致反复催件
- 唐映秋·项目流程协调员：补件跟踪与版本交接（f20、f23）；系统=补件日志、区域规则版本（f21）；交接对象=一线与业务负责人；返工点=交接记录字段不足
- 秦芮·数字化工程师：系统与数据支撑（f30–f35）；系统=服务台/台账/文件库；交接对象=一线与审核；返工点=无统一编号、脏数据需保留原行
- 傅景·审核与质量负责人：结论确认与审计（f41、f43、f45）；系统=审计凭证；交接对象=业务负责人；返工点=缺复核留痕需退回
- 叶书·客户协同代表：对外口径与投诉入口（f50、f54）；系统=客户侧记录；交接对象=一线与业务负责人；返工点=模板口径冲突

四、相互矛盾的陈述（保留分歧，不在本节裁决）

1. 版本判定依据不一致：唐映秋说按有效期与确认状态判定、判不了转人工（f24、f25）；林亦舟说实际只能倒查原始版本才能判断责任落点（f11）。规则判定与人工倒查并存。
2. 系统流程与现场流程不一致：顾明岚与唐映秋描述的链路是客户提交→区域核对→补件→服务确认（f01、f20）；林亦舟描述现场先用群消息处理再补填表格（f13），系统记录滞后于真实事件。
3. 验收严格度不一致：顾明岚给的口径是50单中45单一次给出完整缺件清单（f02）；傅景在此基础上加码，要求每条结果都能关联来源与人工复核记录，缺一项不签字（f42）。属加严而非冲突，但需书面统一。
4. 模板口径未收敛：客户要求统一模板，区域服务团队坚持保留本地材料差异（f50 · 叶书·第1轮），与首期"只做完整性提示"的定位（f05）尚未对齐。
5. 单量口径不可比：林亦舟提供的是演练基线（每月800单、平均补件2.4次，虚构样本，f12），顾明岚未给出真实单量；叶书要求以原始记录定义口径、不能比较两张汇总表（f53）。

五、仍待核实

1. 具体一单的单号、日期、区域（六位均未给出，需回访林亦舟补）
2. 群消息记录能否作为时间证据，能否导出
3. 800单样本的取样窗口与抽样方法
4. 模板统一的最终裁决人（叶书与唐映秋交叉确认）

## 任务 2 / 3 · 还原现状流程

**交付物：现状流程图与异常路径**

一、现状流程（节点编号，标注输入/交接/人工判断/输出）

上游承接：业务挖掘已确认目标（f00）为减少重复核对并保留人工确认与可追溯，首期只覆盖一个批次（f05）；本节在此基础上还原"实际怎么做"，不重复论证目标。

N1 触发
　输入：员工入职材料包（客户提交）
　执行：客户协同代表叶书对外接口，一线接收
　输出：入职服务单（来源：f01、f20）
N2 区域核对【人工判断点①】
　输入：服务单 + 区域清单版本
　执行：一线服务专员林亦舟核对材料完整性
　输出：缺件项清单 / 退回补件
　实际做法：先在群消息里确认再回填表格，**系统记录时间晚于真实发生时间**（f13）
N3 补件跟踪【交接点】
　执行：流程协调员唐映秋
　交接要求：记录接收人、版本、未结项（f20）；不能只发"已处理"，须列最新版本、未确认事项与截止时间（f23）
　输出：补件日志（f21）
N4 版本判定【人工判断点②】
　规则：版本有效期 + 确认状态双条件，作废记录保留原因（f24）
　冲突处理：两边都自认有效→转人工复核；未确认项归到对方名下→责任冲突，规则不允许（f25）
N5 服务确认【人工判断点③】
　权限：一线可提交变更，正式确认必须业务负责人完成；**模型无审批权**（f22）；正式结论须授权人员确认，禁止"系统自动定论"和一线代签（f41）
N6 归档与审计
　要求：原始版本、修订原因、确认人可追溯；练习结束删除虚构个人字段（f43）；审计能还原谁查过、哪个版本、提了什么建议、谁确认（f45）

二、异常路径

E1 版本不一致 → 客服反复催件、逐个确认对方手里哪一版（f10）→ 责任无法归属，需倒查原始版本（f11）
E2 交接只有"已处理" → 未结项挂账，责任断点（f23）
E3 回填时间污染 → 工时按回填时间统计会虚高，必须用业务发生时间（f13 + f34 双时间记录）
E4 读取失败 → 保留上次快照并标记时间，提示人工核查，不编造最新状态（f35）
E5 无法确认版本或关键字段 → 强制进入人工处理队列，必要时暂停试点，不得默认通过（f44）
E6 客户投诉 → 登记原始问题、相关版本与恢复需求，再拉团队确认（f54）
E7 模板口径冲突 → 客户要统一模板 vs 区域保留本地差异（f50），**当前未解决**，首期以完整性提示规避（f05）
E8 数据质量问题 → 重复编号、空时间、版本断链、单位差异四类检查，问题记录保留原行（f33）

三、理想流程与现场做法的差异

1. 理想：客户提交→区域核对→补件→服务确认，四段顺次流转（f01、f20）
   现场：群消息先行处理、事后补填表格（f13），系统链路滞后于真实事件，形成两套并行记录。
2. 理想：版本由规则判定（f24）
   现场：规则判不了时靠人工倒查原始版本（f11），判定人依赖个人经验。
3. 理想：交接有标准字段（f20、f23）
   现场：交接质量取决于个人是否写全，缺字段即产生挂账。

四、只能由人完成的判断（不可自动化）

1. 清单版本有效性判定（f24）
2. 责任归属判定（f11）
3. 正式结论与服务确认（f22、f41）
4. 兜底转人工与暂停决定（f44）
5. 对外承诺与客户口径确认（f52）

五、瓶颈与责任人

B1 版本判定与责任归属 — 责任人：一线服务专员林亦舟（f11）
B2 交接记录完整性 — 责任人：项目流程协调员唐映秋（f23）
B3 工时口径（回填时间 vs 业务发生时间）— 责任人：一线服务专员 + 数字化工程师秦芮（f13、f34）
B4 缺件清单可读性（需要一页清单+来源位置）— 责任人：一线服务专员（f15）
B5 无统一关联编号，跨节点无法串联同一单 — 责任人：数字化工程师秦芮（f30）
B6 复核留痕缺失导致退回 — 责任人：审核与质量负责人傅景（f42、f45）

六、仍待核实

1. 群消息能否作为时间证据导出（影响 B3 的取证方式）
2. N4 人工复核的触发阈值与复核人是谁（f25 只说明"判不了转人工"，未指定人）
3. 真实单量与耗时（当前仅有虚构演练基线 f12）

## 任务 3 / 3 · 四来源收敛与材料核对

**交付物：四来源收敛表、证据台账与问题清单**

一、四来源登记

- Buyer（业务目标）：顾明岚·业务负责人·第1轮 —— 目标减少重复核对并保留可追溯（f00）；验收抽查50单≥45单（f02）；四周/两人/每周≤4小时（f03）；范围由业务方定、审核与质量负责人可否决（f04）；首期单一批次、只做完整性提示（f05）
- Brief（书面范围）：案例资料 case-BRIEF / case-SCOPE —— 六角色清单；边界为只读核对与人工交接；合成训练不代表真实授权、业务执行或客户验收；样本为"一次具体事件"，未提供
- Industry（技术可行性）：秦芮·数字化工程师·第1轮 —— 三类工具无统一编号（f30）；关键字段与缺失值/未确认值区分（f31）；仅脱敏只读导出（f32）；四类质量检查（f33）；双时间记录（f34）；故障保留快照（f35）
- Operator（现场故障与规则）：林亦舟 f10–f15、唐映秋 f20–f25、傅景 f40–f45、叶书 f50–f55 —— 版本不一致反复催件（f10/f11）；群消息先行后回填（f13）；交接字段（f20/f23）；版本判定规则（f24/f25）；权限（f22/f41）；审计与兜底（f43/f44/f45）；模板冲突（f50）；评估三指标（f51）

二、四来源收敛表

【一致项（可直接进入需求定义）】
C1 目标一致：减少重复核对 + 提高可追溯 —— Buyer f00 与 Brief 书面范围表述一致
C2 链路一致：客户提交→区域核对→补件→服务确认 —— Buyer f01 与 Operator f20 四节点相同
C3 时间口径一致：必须用业务发生时间 —— Operator f13（回填时间不等于发生时间）与 Industry f34（同时记录业务发生时间与系统接收时间）互证
C4 权限边界一致：正式确认必须人工 —— Operator f22（模型无审批权）、f41（禁止系统自动定论与一线代签）与 Brief 边界（只读核对与人工交接）一致
C5 读写范围一致：只读不写回 —— Industry f32（写回/外部消息/执行接口不开放）与 Brief 边界一致

【分歧项（保留，不强行统一）】
D1 版本判定依据：唐映秋给的是"版本有效期+确认状态"双条件规则判定（f24、f25）；林亦舟说实际只能倒查原始版本判断责任（f11）。Industry 侧无统一关联编号（f30），短期难以自动判定，两者会长期并存。
D2 验收严格度：Buyer 口径为50单中45单一次给出完整缺件清单（f02）；审核侧加码为每条结果须关联来源与人工复核记录、否则不签字（f42、f45）。属加严，需书面统一后才能作为闸门口径。
D3 模板口径：客户要求统一模板，区域服务团队坚持保留本地差异（f50），而首期定位只做完整性提示（f05）——三方尚未收敛。
D4 记录源不统一：系统链路（f01、f20）与现场群消息（f13）并行，同一事件有两套时间与两套载体。
D5 单量口径：唯一数据是演练基线每月800单、平均补件2.4次且明确为虚构样本（f12），无真实单量，Buyer 侧未给出数值。

【证据不足项（待采集）】
E1 无统一关联编号，四来源无法对齐到同一单（f30）
E2 真实单量、平均耗时、返工率、复核人力成本未测量
E3 群消息记录能否导出，未验证
E4 f25 只说明"判不了转人工"，未指定复核人与触发阈值

三、材料核对（制度 / 日志 / 单据 / 观察）

- 制度：版本有效期+确认状态判定（f24）、责任冲突不允许（f25）、正式结论授权人员确认（f41）→ 可支持"权限与判定规则存在"，不能证明现场执行到位
- 日志：补件日志（f21）与交接记录（f20、f23）→ 可支持补件次数与交接完整性统计；**不能支持工时统计**，因缺业务发生时间
- 单据：脱敏入职清单、区域规则版本（f21）→ 可支持版本核对；属合成样本，非原始授权件
- 观察：群消息先行处理（f13）→ 支持"系统记录滞后于真实事件"的判断，但在不能导出前不可作为时间证据
- 交叉结果：单据与陈述在"交接须记版本与未结项"上一致（f20 vs f21）；观察与制度在"版本如何判定"上不一致（f13/f11 vs f24）

四、问题清单（按优先级）

P1 版本判定规则与人工倒查并存 —— 责任：唐映秋出规则、林亦舟提供现场判定实例；影响责任归属
P2 工时口径被回填时间污染 —— 责任：秦芮落实双时间记录、林亦舟配合取样；影响基线可信度
P3 交接记录字段不足导致挂账 —— 责任：唐映秋；影响责任转移时点
P4 无统一关联编号 —— 责任：秦芮；影响四来源对齐与抽样
P5 验收口径待统一（50/45 vs 留痕加码）—— 责任：顾明岚与傅景书面确认
P6 模板口径未裁决 —— 责任：叶书与唐映秋交叉确认
P7 真实单量与耗时缺失 —— 责任：林亦舟提供样本窗口与单量

五、本轮结论
